    51→    51→## 2. Architecture decisions (record them in `docs/ADR/0004-custom-email-otp-auth.md`)
    52→    52→
    53→    53→- **Do not use NextAuth** for this. Its credentials and email flows fight a single-route SPA and a hand-rolled OTP lifecycle. Build small, readable custom auth on Prisma and Node `crypto`. Explain this in the ADR, including why `next-auth` stays unused (you may leave the dependency alone).
    54→    54→- **Passwords:** `crypto.scrypt` with a random 16-byte salt, N=2^15, r=8, p=1, 64-byte key, stored as a self-describing string (`scrypt$N$r$p$salt$hash`) so parameters can change later. Compare with `crypto.timingSafeEqual`. Minimum length 8, maximum 128, no composition rules that annoy children; show a plain strength hint.
    55→    55→- **Sessions:** 32 random bytes (base64url) as the token. Store only its **SHA-256 hash** in the database. Cookie `lumio_session`: `HttpOnly; SameSite=Lax; Path=/; Secure` in production; 30-day sliding expiry (refresh `lastSeenAt` and expiry at most once per hour). In Next 16, `cookies()` is async. For state-changing requests also reject a mismatched `Origin` header (a cheap CSRF defence consistent with the capstone cut).
    56→    56→- **OTP:** 6 digits from `crypto.randomInt`, zero-padded. Store `HMAC-SHA256(AUTH_SECRET, email + ":" + purpose + ":" + code)`, never the code. 10-minute expiry, **5 attempts then the code is dead**, single active code per (email, purpose) (a new send invalidates the old one), 60-second resend cooldown, at most 5 sends per email per hour and 20 per IP-hash per hour (in-memory limiter is acceptable; the stack says local memory caching only). Compare hashes in constant time. A used code can never be reused.
    57→    57→- **Anti-enumeration:** requests that start a flow (sign up, code sign-in, forgot password) return the **same response and similar timing** whether or not the account exists. If someone signs up with an existing verified email, quietly send "you already have a Lumio account, sign in instead" rather than revealing it in the response. Sign-in errors say "That email or password didn't match" and nothing more specific.
    58→    58→- **Lockout:** 5 failed password attempts lock sign-in for that account for 15 minutes (`failedAttempts`, `lockedUntil`); respond with the same generic message plus a calm "try again in a few minutes", and always allow the email-code route as an alternative.
    59→    59→- **Why an OTP and not a link:** a code works on a phone where the email app and Lumio are different apps, survives link scanners, and has nothing to phish. Emails contain **no links and no tracking pixels**.
    60→    60→- **Secrets:** `AUTH_SECRET` is required in production (refuse to start in production without it, with a clear message). In development generate and print a one-time warning if it is missing, and use a per-process random value.

   136→   136→## 5. API contract (route handlers under `src/app/api/auth/*`)
   137→   137→
   138→   138→All responses are JSON with a stable shape `{ ok: boolean, code?: string, message?: string, ... }` where `code` is from a closed list and each code maps to a calm learner-facing string in `i18n.ts`. Validate every body with Zod; reject unknown fields; trim and lowercase emails; cap body size.
   139→   139→
   140→   140→| Route | Purpose | Notes |
   141→   141→| --- | --- | --- |
   142→   142→| `POST /api/auth/signup` | name, email, password, ageBand, emailOwner | Creates an **unverified** user (or silently no-ops for an existing email), sends a `signup` OTP. Same response either way. Under-18 learners: see Section 6. |
   143→   143→| `POST /api/auth/verify` | email, purpose, code | Validates OTP; for `signup` sets `emailVerifiedAt`, creates a session, and returns freshly generated **recovery codes once**. For `login` creates a session. For `reset` returns a short-lived single-use reset ticket (HMAC-signed, 10 min) bound to that email. |
   144→   144→| `POST /api/auth/login` | email, password | Generic failure message; lockout rules; if the account is unverified, send a fresh `signup` OTP and respond `NEEDS_VERIFICATION`. |
   145→   145→| `POST /api/auth/otp/request` | email, purpose (`login` or `reset`) | Passwordless sign-in and forgot password. Always returns the same response. |
   146→   146→| `POST /api/auth/reset` | ticket, newPassword | Sets the password, **revokes every session**, consumes the ticket. |
   147→   147→| `POST /api/auth/recovery` | email, recoveryCode, [newPassword] | Signs in (or resets) with a one-time recovery code; marks it used; reports remaining codes. |
   148→   148→| `POST /api/auth/recovery/regenerate` | (signed in) password or fresh OTP | Replaces all recovery codes. |
   149→   149→| `POST /api/auth/logout` | | Deletes this session. A `?all=1` variant deletes all of the user's sessions. |
   150→   150→| `GET /api/auth/me` | | Returns `{ signedIn, user: { id, name, email (masked), ageBand, aiEnabled } }` or `{ signedIn: false }`. Never errors the app; the app boots first from local data and calls this afterwards. |
   151→   151→| `POST /api/auth/delete` | password or fresh OTP, typed confirmation | Deletes the user and all server-side data. Local learner data stays on the device unless the learner also resets it; say so on screen. |
   152→   152→| `GET /api/capabilities` | | `{ email: { mode: 'console'|'smtp'|'off', reason }, ai: {...} }` so the UI shows or hides features truthfully. |
   153→   153→
   154→   154→Recovery codes: 8 codes of the form `XXXX-XXXX` (unambiguous alphabet, no 0/O/1/I), stored hashed, each single-use. Show them once with Copy and Download (`.txt` Blob) and require the learner to tick "I've saved these" before continuing.

   248→   248→## 11. The features (build in this priority order; each behind its own flag and hidden when AI is off)
   249→   249→
   250→   250→Each feature has: an API route under `src/app/api/ai/*`, a Zod input and output schema, a prompt file, a fake-adapter fixture, a degradation path, i18n strings, and a verified end-to-end demo.
   251→   251→
   252→   252→### Tier 1 (must ship)
   253→   253→
   254→   254→1. **Study Buddy (Socratic tutor).** Entry points: the Reader (per chapter) and a floating "Ask" affordance from Study. Streams replies over **SSE** with a plain polling or non-streamed fallback. **Grounded** on the open chapter: build a compact context from `chapterContent.ts`/`content.ts` (key points, glossary, sentences), cite the chapter id, and **decline out-of-scope questions** while saying what it *can* help with. Socratic by default: a **hint ladder** (nudge, bigger hint, worked step, answer only when asked twice). Persona by band: *young* at most two short sentences and offers read-aloud via the existing `speechSynthesis` code; *school* concise; *adult* detailed. Replies in the learner's language (English, Hindi, Hinglish). Keep chat history in memory for the session only; optionally store nothing server-side.
   255→   255→2. **Explain my mistake.** In Quiz results and the Mistake Notebook: input is the question, the learner's answer and the key (plus the stored explanation); output (schema-validated JSON) is a level-appropriate explanation, the likely misconception, and **one** remedial practice question. Practice-only, no XP. Falls back to the authored explanation when AI is unavailable.
   256→   256→3. **Notes to summary, flashcards and quiz.** Builds on the existing sanitised note upload in `StudyTools.tsx` (plain text only, 200 KB cap). Per-document consent checkbox before sending anything ("Send this note to the AI helper?"), output labelled "AI summary of your document". Returns summary bullets, glossary terms, up to 10 flashcards and 5 questions, validated with Zod. Save results through **new bounded events** handled by pure `applyEvent` cases (replay-safe, deduped by id), stored separately from authored content, practice-only.
   257→   257→
   258→   258→### Tier 2 (should ship)
   259→   259→
   260→   260→4. **Practice generator (beta).** "More questions like this" for a chapter. Generates items to the existing question schema. Automated checks before display: the schema validates, a **second independent solve** agrees with the key, and numeric answers are re-verified where possible; otherwise the item is dropped. Clearly labelled "Beta practice, AI-written, not reviewed". No XP.
   261→   261→5. **Plan Coach.** Reads *aggregates only*: `weakTopics`, mock results, exam date, free windows, commitments. Returns a structured suggestion for the next 7 days that is **validated against the deterministic scheduler** (`planDayWithOverrides`, `rescheduleOptions`). The learner previews it and taps Accept, which dispatches the existing `session-rescheduled` events. The scheduler stays the source of truth; invalid suggestions are discarded with a kind message.
   262→   262→6. **Code Lab nudge.** In `CodingLab.tsx`, after the authored three-level hint ladder is exhausted, offer "Ask for a nudge": send the learner's code, the failing test output and the exercise statement; reply explains the *error* and the next step **without giving the full solution**. Same safety and labelling rules.

   265→   265→
